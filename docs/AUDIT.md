## 1. Feature Status

### GitHub App Install
**Status: Working**

When the GitHub App is installed, `installation.created` fires and calls `createTeamFromInstallation` + `connectRepo` for each selected repo. A 60-day backfill is immediately triggered via `backfillTeamRepos` (fire-and-forget). Repo additions/removals via `installation_repositories.added/removed` are also handled.

- `apps/api/src/webhooks/github.ts` — event routing
- `apps/api/src/services/teams.ts` — team upsert from installation
- `apps/api/src/services/repos.ts` — `connectRepo`, `disconnectRepo`
- `apps/api/src/services/backfill.ts` — 60-day PR backfill on install
- `apps/api/src/github.ts` — `getInstallationOctokit` (App RSA key)

### OAuth Login
**Status: Working**

`GET /auth/github` → GitHub OAuth → `GET /auth/github/callback`. On callback, user is upserted, a 7-day JWT session is created, and the `grassion_session` cookie is set (`SameSite=None; Secure` in production). Referral code in OAuth `state` is captured. Welcome email sent on first login.

- `apps/api/src/routes/auth.ts`
- `apps/api/src/auth.ts` — `createSession`, `setSessionCookie`

### GitHub Webhooks (PR events)
**Status: Working**

Handles `pull_request.{opened, edited, closed, reopened, synchronize, labeled, unlabeled}` and `check_run.completed`. Each delivery is deduplicated by `X-Github-Delivery` ID (inserted into `webhook_events` with `ON CONFLICT DO NOTHING`). HMAC-SHA256 signature verified before processing.

On merge, demo mode is cleared if the repo is not `grassion-demo`, outcome checks are scheduled (7/14/30d), and an instant Slack alert fires if the title starts with `Revert `.

- `apps/api/src/webhooks/github.ts`
- `packages/db/src/schema.ts` — `webhookEvents` table (idempotency)

### AI-PR Detection
**Status: Working**

Priority order (cannot be bypassed):

1. `grassion:ai-<tool>` / `grassion:human` label — confidence 1.0
2. Co-authored-by commit trailers matching Copilot/Claude/Cursor/Windsurf — confidence 0.95
3. PR body regex (`generated by`, `🤖`, etc.) — confidence 0.70
4. Statistical pattern (bulk additions, single-commit large writes, fast unreviewed merge) — confidence 0.35–0.45

`unknown_ai` is returned when AI is inferred but the tool cannot be identified.

- `apps/api/src/services/ai-detection.ts`
- `apps/api/src/services/ai-detection.test.ts` — 12 tests, all passing

### Revert / Hotfix Detection
**Status: Working**

**Revert:** `findRevertPR` scans subsequent PRs in the same repo for `Revert "<original title>"` by exact match or 30-character prefix match. Sets `wasReverted`, `revertedAt`, `revertPrNumber` on `pr_outcomes`.

**Hotfix:** `checkHotfixWithin7d` accumulates 5 signals — hotfix/urgent/critical label, title keywords, merge within 30 minutes, off-hours merge (outside 9–18 UTC weekdays or weekend), zero-review fast merge. Any signal sets `hadHotfixWithin7d = true`.

**Limitation:** Hotfix heuristics produce false positives. Off-hours merges and fast merges are normal in small teams; they always fire `hadHotfix = true`. This inflates `hotfixRate` and `reworkScore` for legitimate PRs.

- `apps/worker/src/outcome-tracker.ts` — `findRevertPR`, `checkHotfixWithin7d`
- `apps/worker/src/scoring.ts` — `computeReworkScore`
- `apps/worker/src/outcome-tracker.test.ts` — 6 tests, all passing

### Weekly ROI Verdict
**Status: Working**

Worker computes `teamWeeklyMetrics` for all teams on an hourly cron (for digest) and a 6h cron (outcome pass). `GET /api/metrics/summary` reads from the weekly metrics cache, falling back to a live query. Verdict is `net_positive / net_negative / unclear / insufficient_data` (threshold: < 5 PRs = insufficient).

ROI formula: `estimatedDollarSaved = aiPrs × hourlyRate × 2`; `netDollar = saved − monthlyAiSpend`. This is a simple heuristic — it does not use actual merge-time comparisons unless the worker has computed `aiAvgMergeHours`.

- `apps/api/src/routes/metrics.ts` — `/api/metrics/summary`, `/api/metrics/weekly`
- `apps/worker/src/metrics.ts` — `computeWeeklyMetricsForAllTeams`

### Seat Waste
**Status: Working**

`GET /api/analytics/seat-waste` queries all team users, counts AI PRs merged in the last 7 days per user, identifies inactive seats (count = 0), and returns monthly waste = inactive seats × per-seat cost. Per-tool seat costs are configurable via `tool_seat_costs` JSONB on the team. A `savings_events` row is logged at most once per 24h.

- `apps/api/src/routes/analytics.ts` — `/api/analytics/seat-waste`

### Codebase Health Score
**Status: Working (score computed, snapshots partially populated)**

`GET /api/analytics/health` computes a score live from `pull_requests`:  
`score = max(0, 100 − revertFraction×40 − hotfixFraction×30 − avgChanges×10)`

`GET /api/metrics/summary` also calls `populateWeeklyMetrics` which inserts a `codebase_health_snapshots` row via raw SQL. However, `GET /api/analytics/codebase-health` reads from `codebase_health_snapshots` — if `populateWeeklyMetrics` hasn't run this week, the endpoint returns `{ current: null }`.

**Limitation:** Health snapshots are only written when `/api/metrics/summary` is hit. The worker does not independently write health snapshots. A team with no dashboard visits this week gets a stale or null health score.

- `apps/api/src/routes/analytics.ts` — `/api/analytics/health`, `/api/analytics/codebase-health`
- `apps/api/src/routes/metrics.ts` — `populateWeeklyMetrics` (raw SQL writes to `codebase_health_snapshots`)

### Slack Digest
**Status: Working (alerts) / Partial (weekly Slack digest)**

**Instant alerts:** `sendRevertAlert` fires on `pull_request.closed` (merged) when the title starts with `Revert `. `sendHealthDropAlert` and `sendInactiveSeatAlert` run via `runSlackAlertCheck` — this function is **registered in `apps/api/src/lib/slack.ts` but never called from the worker's cron schedule**. It must be explicitly invoked; the API exports it but does not wire it to a cron.

**Weekly Slack digest:** `runWeeklySlackDigests` sends the `sendWeeklyDigest` message via Slack Block Kit. Like the health-drop alert, this is defined but not wired into the worker's scheduled cron.

**What is wired:** The worker cron calls `sendDigestsForDueTeams` (email digest) and `computeWeeklyMetricsForAllTeams`. The Slack functions live in `apps/api/src/lib/slack.ts` and are not imported by the worker.

### Email Digest
**Status: Working**

Worker runs hourly: computes last week's metrics for all teams, then calls `sendDigestsForDueTeams` which filters teams by `emailDigestEnabled = true` AND `emailDigestDay == today (UTC day-of-week)`. Skips if already sent this week. Sends to owner + admin emails only. Uses Zoho SMTP via nodemailer. Welcome email uses Resend with Zoho fallback.

### Razorpay Billing
**Status: Working**

Two payment flows coexist:

1. **Order flow (primary):** `POST /api/billing/checkout` creates a Razorpay Order. `POST /api/billing/verify` verifies HMAC, sets `plan = starter/team/business` and `subscriptionStatus = active` in DB.
2. **Subscription flow (legacy):** `POST /api/billing/subscribe` creates a Razorpay Subscription (requires `RAZORPAY_PLAN_ID_STARTER` env var). `POST /api/billing/verify` also handles the `razorpay_subscription_id` path.

Razorpay webhook handler (`/webhooks/razorpay`) syncs subscription lifecycle events. Referral conversions recorded on `subscription.activated` and `subscription.charged`.

`planFromStatus` maps only `active` → `'starter'`; all other statuses → `'trial'`. There is no `'team'` or `'business'` plan mapping here — those are only set via the verify endpoint.

- `apps/api/src/billing/razorpay.ts`
- `apps/api/src/routes/billing.ts`
- `apps/api/src/webhooks/razorpay.ts`

### Plan Limits
**Status: Partial — primarily UI-gated, minimal server enforcement**

The only server-side plan gate is `requireActivePlan` in `apps/api/src/auth.ts`. It returns HTTP 402 when `plan === 'trial' && trialEndsAt < now`. Plans `starter`, `team`, `business`, and `admin` bypass this gate entirely.

No server-side enforcement of:
- Repo limits by plan
- Seat count limits
- Feature-level access (CSV export, benchmarking opt-in, API access)

These are mentioned in the spec but handled only in frontend code. Any user with a valid session can call any authenticated endpoint regardless of their plan level.

`TRIAL_EXEMPT_PREFIXES` in `apps/api/src/auth.ts` (lines 14–27) further lists routes that bypass even the trial expiry check (analytics, metrics, prs, team, repos, billing, notifications, webhooks, health, contact, demo).

- `apps/api/src/auth.ts` — `requireActivePlan` (lines 29–53)

## 4. Plan / Tier Enforcement in Code Today

### Server-side (real enforcement)

The only server-side gate is `requireActivePlan` (`apps/api/src/auth.ts:29`):

```
if plan === 'trial' AND trialEndsAt < now → HTTP 402
```

Routes exempt from this check via `TRIAL_EXEMPT_PREFIXES` (lines 14–27):  
`/auth/`, `/api/billing`, `/api/team`, `/api/repos`, `/api/notifications`, `/api/analytics`, `/api/metrics`, `/api/prs`, `/webhooks/`, `/health`, `/api/contact`, `/api/demo`

This means **analytics, metrics, and PR data are always accessible regardless of plan**, even after trial expiry. This is intentional — plan gating is delegated to the frontend.

### Frontend-only gating (not enforced server-side)

The React app (`apps/web/`) reads the `plan` claim from the JWT cookie. Plan-gated features include:
- CSV export (starter+)
- Additional repo slots (team+)
- Benchmarking opt-in (business+)
- Demo seeding lock after trial

There is **no server validation** of these plan boundaries. A user who manually calls the API can bypass all frontend plan gates.

## 5. Secrets in the Repository

`.env` files are correctly listed in `.gitignore` and are **not tracked by git** (confirmed: `git ls-files .env` returns nothing).

However, several `.env` files exist on disk with real credentials that would be exposed if `.gitignore` were ever modified or if the files were accidentally staged:

| File | Issue |
|---|---|
| `.env` | Contains `RAZORPAY_KEY_ID=rzp_test_…` (test key) and `OPENAI_API_KEY=sk-proj-…` (live key) |
| `apps/api/.env` | Contains `RAZORPAY_KEY_ID=rzp_test_…` and a different `OPENAI_API_KEY=sk-proj-…` |
| `apps/web/.env` | Contains `VITE_RAZORPAY_KEY_ID=rzp_live_…` (**live** Razorpay publishable key) |
| `apps/worker/.env` | Contains `OPENAI_API_KEY=sk-proj-…` (same as api) |

**No secrets are hardcoded in tracked `.ts` / `.js` source files.** All secrets are loaded via `env()` from `process.env`.

**Missing:** There is no `.env.example` file in the repo root. New developers have no reference for which environment variables are required.

**Recommendation:** Add a `.env.example` with all keys listed but values blanked. Rotate the OpenAI key in `apps/api/.env` and `apps/worker/.env` if they differ from the production value already in Fly.io secrets (the disk files may be stale).

## 7. Pre-Feature Risks

1. **Hotfix heuristics over-fire.** The `off_hours` and `zero_review_fast` signals fire on every off-hours merge and every small same-day fix. Small teams regularly merge after hours. This inflates `triggeredHotfix` and `reworkScore`, causing false problem-PR notifications and an artificially low health score. **Fix before adding any feature that depends on hotfix rate accuracy.**

2. **No `.env.example`.** New contributors or a second developer have no documented list of required environment variables. The app silently exits on startup if any required var is missing — the error message is printed to stderr only.

3. **Slack alert functions not wired into the worker cron.** `runSlackAlertCheck` and `runWeeklySlackDigests` are defined in `apps/api/src/lib/slack.ts` but never imported by `apps/worker/src/index.ts`. Slack digests and health-drop alerts will never fire until this import is added.

4. **`codebase_health_snapshots` only populated on dashboard visit.** `populateWeeklyMetrics` is called from `/api/metrics/summary` (an API route), not from the worker. Teams that haven't loaded the dashboard this week have no health snapshot, so `/api/analytics/codebase-health` returns `{ current: null }`.

5. **`pr_risk_signals` and `engineering_events` tables exist but are never written.** Code that references these tables in `schema.ts` is schema-only. Any new feature that reads from them will see empty results.

6. **Plan enforcement is entirely frontend-side.** Any authenticated HTTP call bypasses all plan gates. If a paid feature is added, it must be enforced at the API layer, not just in the UI.

7. **`planFromStatus` maps only `active` → `starter`.** If Razorpay ever sends a status other than `active` for a paying subscription (e.g. `authenticated` at the start of a subscription cycle), the team's plan is silently downgraded to `trial`. The Razorpay webhook handler calls `planFromStatus` for all lifecycle events including `subscription.charged`.

8. **Backfill uses installation token only.** `backfillTeamRepos` calls `getInstallationOctokit` which requires `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, and a valid installation. If these are missing (e.g. local dev), backfill throws and no historical PRs are loaded. The error is caught and logged but no fallback exists.

9. **OpenAI monthly budget cap is enforced in the worker but not the API.** `GET /api/analytics/pr-outcomes` generates OpenAI summaries on-the-fly for up to 3 missing rows per request (`apps/api/src/routes/analytics.ts:753`). These calls go through `generatePrSummary` in `apps/api/src/lib/ai-summary.ts` but that path does **not** consult `llm_usage_log` or `OPENAI_MONTHLY_BUDGET_USD`. The budget guard only exists in `apps/worker/src/llm/pr-summary.ts`. High dashboard traffic could run up unbounded OpenAI spend via the API path.

10. **Migration 0019 may not be applied in production.** The RFG tables (`rfg_analysis_runs`, `rfg_pr_labels`, `rfg_pr_file_paths`) are in `packages/db/migrations/0019_repeat_failure_guard.sql`. The API will throw a DB error on any `/api/rfg/*` request if this migration has not been applied to the production Supabase instance.
